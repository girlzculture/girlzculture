## Documented source contract

The implementation pins `v26.0`, requests only `instagram_business_basic`, and uses Instagram Login for professional Business/Creator accounts. Official public documentation was retrieved on 2026-09-19; copies are in `work/redesign-evidence/instagram-official-*.html` and `.txt` outside Git.

- [Business Login](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login/) documents authorization and the multipart token exchange. The exchange response contains `data:[{access_token,user_id,permissions}]`; that `user_id` is app-scoped. The short-lived token is sufficient for this bounded import and is erased after a successful read; no refresh token or ongoing access is requested.
- [Instagram Login getting started](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/get-started/) distinguishes `/me.id` (app-scoped) from `/me.user_id` (professional account). Both identities are verified and stored separately. Profile fields are `id,user_id,username,name,account_type`.
- [Media reference](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-media/) supports owned media identity/type/URL/time. Current documentation labels captions as Facebook Login-only; the adapter does not request captions or infer missing biography/services/prices/hours/team/policies. It reads at most 16 own still images, marks an excerpt when more or unsupported video/carousel content exists, and never follows provider pagination URLs.
- [Data-deletion callback](https://developers.facebook.com/docs/development/create-an-app/app-dashboard/data-deletion-callback/) specifies a signed request and an opaque confirmation/status URL. The callback verifies HMAC, algorithm, issued time and app-scoped identity. [Manual Login flow](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/) documents deauthorization configuration. Exact Instagram app callback delivery remains an external acceptance gate.

## Authorization, review and media

Only the current active business owner with `my_page` access may authorize/read/create the private draft. State is browser-cookie bound, hashed in storage, ten-minute expiry, generation bound and consumed once. Stored credentials use AES-256-GCM with business-specific authenticated context. A previously bound other-business app account is rejected before reading its profile; SQL checks the professional-account binding again when saving authorization. Disconnecting/finishing a source read does not release that binding or grant another business access.

The configuration must explicitly approve acceptance/live activation, match the exact configured HTTPS callback origin, and have the app credentials plus a 32-byte encryption key. Acceptance is restricted to the configured owner on the configured deployment. Live additionally requires recorded verification and the production callback origin. Missing configuration gives an honest unavailable state and leaves manual setup available. No credentials are exposed to the browser, assistant, logs or error responses.

An import reserves a single writer and each private image path before uploading. Only documented owned-media IDs are read; downloads use allowed Meta image-CDN HTTPS hosts, no redirects, bounded bytes and deadlines. The shared canonical image decoder validates/normalizes images and verifies stored checksums. Staged images live in the private originals bucket; selected facts reference opaque asset tokens. Draft creation is idempotent for the exact request and selected facts. No canonical profile/gallery is modified at this stage.

The existing saved draft, moderation and six-section confirmation remain authoritative. Only after explicit confirmation can a selected own staged image be prepared at its deterministic own public path. The database atomically resolves exact prepared own asset tokens during the existing onboarding apply, preserving baseline/revision/owner checks and the unpublished-new-business or explicit-existing-public-impact behavior. An uncertain response cannot silently claim application. An authorized confirmation that fails application may leave an unlisted prepared public object pending cleanup; it is not attached to the gallery.

## Disconnect, deletion and retention

Owner disconnect invalidates credentials/flows; saved private drafts remain available until expiry. Verified provider deauthorization/data-deletion invalidates credentials/flows first, blocks new authorization during pending deletion, removes only provenance-bound imported image URLs, and purges private/provider data and exact reserved objects. Independent owner-entered services, hours, policies and changed identity text are preserved. Canonical business facts explicitly confirmed/edited by the owner are not erased merely because a provider source is deleted. This distinction must be reviewed against the approved Meta application/privacy policy before activation; it is not asserted to satisfy every provider/legal obligation.

Uploads have bounded transport and reservation leases. Deletion remains pending while a reserved upload may still write; it does not falsely report completion. Exact retries and the existing protected daily `/api/media/cleanup` job continue pending deletion safely. Cleanup accepts only durable own UUID-bound paths, never callback-supplied paths or buckets.

Expired OAuth flows and expired access credentials are removed. Abandoned source reads become eligible for cleanup after an hour; unused private imports expire after seven days. The daily job removes expired private/prepared objects and redacts provider-only draft fields while retaining independent owner edits. Applied imports lose private originals after seven days; explicitly approved public gallery content and minimal provenance needed for future deletion remain until an explicit deletion action. There is no new scheduler, provider write or production configuration change.
