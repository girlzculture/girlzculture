# Inherited schedule payment-method support

Status: **IN PROGRESS / AUTOMATED ONLY / NOT RELEASED**. No real Stripe request, payment, invoice, schedule mutation or production migration was performed for this work.

The original server rejected every attached subscription schedule before opening setup. A simulated inherited schedule reproduced that409; the preserved log is `redesign-evidence/payment-schedule-before.log` outside Git.

The supported subset is an active schedule bound to the authenticated business's exact stored subscription/customer and Stripe mode. Its current and future phases must explicitly return null default methods, have complete sequential dates and recognized item/phase fields, and contain no legacy source override. Explicit phase overrides, missing fields, unknown top-level/phase/item fields and unsupported objects remain review-required. This does not claim support for every scheduled agreement.

Setup retains the existing Stripe customer, setup-only Checkout and immutable attempt generation. Migration178 adds the original schedule object and canonical schedule/subscription fingerprints, a separate schedule-stage first-send time, verification time and safe request ID. The only schedule write parameter is `default_settings[default_payment_method]`. No phase, price, quantity, date, tax, discount, cancellation, release, invoice or proration value is sent. If the current subscription does not inherit immediately, its existing default-only update runs as a separate durable stage with a separate idempotency key/time. Success requires both authoritative objects to resolve to the target and all captured commercial values to remain unchanged.

Lost delivery is reconciled by reads first. A target already applied is not sent again. Unresolved stages may retry only the same stable key/target within23hours of their own persisted first-send time. An older stage can finish only by read-only reconciliation; external defaults, changed phases or changed associations stop the operation. No automatic restoration of an old provider snapshot occurs.

Plan-change and lifecycle routes now share an owner/subscription-bound mutation guard with method reservations. Provider calls have one45second deadline, and the database lease has a two-minute envelope with a one-minute remaining-time pre-write check. Both directions use the same transaction mutex and active-attempt exclusion. A provider-write latch survives lease expiry when delivery is uncertain. A validation failure before any provider write releases its lease; only an allowlisted parameter-rejection400 plus unchanged authoritative baseline reads can clear a first rejected write. Payment-required402, idempotency409, network failures and5xx do not establish no mutation.

Ambiguous multi-step plan/lifecycle results require billing reconciliation. Their exact frozen request parameters, stable keys, baseline hashes, first-send times and allowlisted provider request IDs remain in a private service-only relation. Browser APIs return a specific409 and the exact protected Engine incident reference. No automatic retry of an uncertain commercial operation or administrative hold-clearing endpoint is introduced. The same verified in-flight operation can finish normally; a different generation cannot release its hold. This limitation is explicit and must be included in release review.
