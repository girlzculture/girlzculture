# Business referral acceptance

Status: **AUTOMATED ONLY**. Campaigns are inactive until their actual terms are configured and founder-authorized. This implementation has not activated any real campaign, issued a reward, changed Stripe, or applied a production migration. USD20 is not a default or approved campaign. No free month is promised.

## Implemented boundaries

- Migration `20260919043012_business_referral_campaigns.sql` adds private campaign configuration, opaque owner codes, one lifetime referral attribution per referred business, immutable accepted terms, entitlement records referencing the existing `billing_events` ledger, and audit events. Every table enables RLS and revokes browser-role access; server RPCs use `SECURITY INVOKER` and real owner/platform-owner checks. It seeds one incomplete inactive campaign with null amount, recipient and dates.
- The Engine configuration API saves inactive drafts with an expected revision. Configurable terms are USD amount, recipient (referring or referred business), start/end, minimum collected payment, qualification window, review hold, and per-referrer campaign limit. Saving pauses the campaign; previous claims keep their accepted terms. Activation requires a separate exact-term founder-reviewed operation. No activation or issuance HTTP action is exposed.
- The owner flow creates/resumes an opaque code, accepts another business's code only after explicit term confirmation, preserves durable attribution across retries, and provides fresh own-business status. It rejects self-referrals, duplicate attribution, previously active/paid subscriptions, shared provider customers and owner changes. A serialized cap check prevents simultaneous refreshes creating excess eligible entitlements.
- Qualification uses canonical subscription status and the signed billing-event path. A paid invoice label alone is insufficient. Proof requires matching existing customer/subscription/business, live automatic collection, a succeeded PaymentIntent and captured, undisputed, unreversed charge with matching amount/currency/customer. Explicit fraudulent reporting or any linked provider review holds qualification for billing review, even if the payment is captured and undisputed. Both legacy invoice PaymentIntent and current invoice-payment relationships are supported; ambiguous/mixed funding fails closed. Optional webhook enrichment is gated on an actual referred claim and must not block the canonical ledger when a provider read fails.
- Private verification observations reference canonical billing-event IDs without changing canonical money snapshots. A bounded owner refresh rechecks current invoice, subscription and payment evidence using provider GETs only. Failed checks invalidate old positive observations; a generation token prevents an older response overwriting a newer disputed/failed result. Stale or unverified observations put owner-visible entitlements on hold. Customer/payment identities cannot earn separate duplicate entitlements through multiple referred businesses. Existing entitlements remain tied to their original payment; a later invoice cannot hide its reversal. A twenty-first queued payment produces an explicit pending result for the bounded twenty-payment refresh.
- Activation and payment must occur after attribution and within configured dates/window. Existing ledger refunds/credits hold the reward; ended/cancelling subscriptions and identity changes require review. Qualifying records are **pending review**, never issued credit or collected revenue. The review-hold date is shown honestly. There is no financial transfer/credit/charge operation or second money ledger.
- Owner and assistant projections contain only that business's own entitlement amount/status/campaign/dates. They never expose referred-business identity, customer details, invoices, plans, code usage or provider IDs. The assistant helper is an allowlisted projection, not permission to retrieve other businesses.
