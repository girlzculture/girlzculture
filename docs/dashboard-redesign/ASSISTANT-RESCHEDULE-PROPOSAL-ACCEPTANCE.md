## Existing gap and bounded change

`assistant-reschedule-before.log` records the missing tool contract: the assistant rejected `prepare_booking_reschedule_proposal` as `ASSISTANT_UNKNOWN_TOOL`. The existing manual reschedule action correctly refused marketplace bookings. The new action connects the assistant to the established marketplace proposal/customer-response workflow; it does not introduce a second rescheduling system.

The new bookings-permission, risk-four action prepares one alternative date/time with the current professional, booked duration, agreed price and deposit unchanged. The review contains the actual customer/reference, current and proposed times, service, professional and financial terms. The owner must explicitly confirm sending the proposal. Preparation reads canonical availability and can persist an assistant draft/audit, but creates no booking proposal, customer management token or notification. Ambiguous names or missing dates require clarification; supplied booking selection facts include origin, total count, shown count and excerpt status. The language-model selection contract is tested with simulated responses; real-provider interpretation of natural voice intent is not claimed.

The existing reschedule server separates read-only validation from delivery. Confirmation invokes the same canonical `create_booking_reschedule_proposal` function through an atomic assistant wrapper. It rechecks authorization, assignment, the exact preview/booking/payment snapshot, current professional, hours and calendar occupancy, then saves one Pending proposal and assistant audit and reads the durable proposal/option back. The booking is unchanged. Only the existing authenticated customer-response process may accept or decline it. The owner-side assistant has no customer-consent argument or execution path.

After successful confirmation, the route uses the existing guest-link and per-channel notification delivery system, including its deduplication. A transport failure preserves the verified proposal and returns a warning with the protected incident reference. Management URLs, contact fields and tokens never enter the assistant response/model context. Replays recheck actual proposal/options and show Pending, Accepted, Declined or Expired status truthfully; missing durable evidence refuses success. Existing manual appointment workflows remain unchanged.
