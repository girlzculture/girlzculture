# Subscription payment method: frozen implementation and acceptance

Snapshot: 2026-09-19 UTC. This records the current PR #80 implementation; it is not a declaration of live Stripe acceptance. No production migration or provider write was performed for these checks.

## Current behavior

An authenticated business owner can start setup-mode Stripe Checkout for the customer and subscription already linked to that business. Staff cannot start, complete, or cancel the update. The setup session and SetupIntent carry the same attempt, business, and subscription association; completion independently verifies their status, customer, mode, and environment before using the resulting attached card.

For subscriptions without an attached schedule, the application requests only `subscription.default_payment_method` when applying the card. For the supported inherited-default schedule subset, it updates only `default_settings[default_payment_method]` on the existing schedule and, if needed, the existing subscription default as a separate durable stage. It never sends phase, price, quantity, date, tax, discount, cancellation or proration fields, creates a replacement customer/subscription, issues an invoice or requests a payment. Fresh provider readback must confirm the effective card and unchanged captured commercial fields before success. The owner sees only brand, last four digits, and expiry. Existing customer-level defaults and unrelated subscriptions are not modified. Setup follows Stripe's documented [setup-mode Checkout flow for updating subscription payment details](https://docs.stripe.com/payments/checkout/subscriptions/update-payment-details).

`GET /api/stripe/portal` returns the authoritative masked card, actual test/live mode, pending state, and update availability. `POST` supports begin, complete by setup-session ID, and cancel by attempt ID. Cancellation expires an open setup session and rechecks its status; a session already completed is reconciled rather than falsely reported as cancelled. Terminal responses distinguish `updated`, `cancelled`, and `expired`, so an expiry webhook arriving before either browser return cannot be mistaken for pending work. Replaying a terminal outcome performs no provider write.

The current flow rejects ended subscriptions and unsupported attached schedules. **Inherited-default support is implemented through178; bounded explicit-phase support is implemented through187.** The latter requires a recognized pinned snapshot and exact retained original intent, freezes the full unchanged commercial phase payload before changing method fields, and verifies both schedule and subscription. Unknown or ambiguous legacy intent, stale agreements and one-off invoice-item phases remain review-required. Actual sandbox acceptance remains unverified; see [the schedule acceptance record](PAYMENT-SCHEDULE-ACCEPTANCE.md).

The failed request used the live account, where those sandbox objects do not exist. This is a demonstrated provider-account/environment mismatch, not a missing subscription to recreate. The new setup flow does not change production credentials or convert sandbox objects into live billing identities. **Real Stripe setup, cancellation, masked readback, and agreement-preservation acceptance remain blocked/unverified.** The protected sandbox-only workflow and scripts are implemented using the confirmed existing identities, but have not been dispatched; their environment credential and webhook-routing gates remain documented in [BILLING-SANDBOX-VERIFICATION.md](BILLING-SANDBOX-VERIFICATION.md). Production's live key must not be replaced for this check. Local mocked-provider tests do not establish provider behavior. No customer was recreated or relinked as a workaround.

## Recovery and access controls

- One active durable attempt is allowed per business and per subscription; completed/cancelled generations cannot be reset or reused.
- Reservation, claim, and first-apply checks validate the current owner and stored customer/subscription association. The private attempt table is RLS-protected; RPCs use `SECURITY INVOKER` and service-only execution, with narrowly scoped identity-column grants.
- A two-minute database lease coordinates return-page and webhook handlers. A shared 45-second provider deadline bounds the entire operation, including readback.
- Setup creation and application use stable per-attempt idempotency keys. Uncertain delivery preserves the attempt for reconciliation. Stripe documents that keys can be pruned after 24 hours, so application retries fail closed after 23 hours from the durable first-apply timestamp unless read-only inspection already confirms the intended method. See [Stripe idempotency behavior](https://docs.stripe.com/api/idempotent_requests).
- Before the first application, a fresh effective-method comparison rejects a stale setup session if the method changed externally. The bound SetupIntent and target method are immutable.
- Unbound setup creation stops after 29 minutes: the original one-hour expiry must retain Stripe's minimum 30-minute creation window. The application never silently changes an uncertain creation request or starts another generation.
- A payment-method-only subscription webhook does not rewrite commercial plan or publication state from a potentially stale event snapshot. Other existing booking and subscription webhook paths remain separate.

## Attached schedules: implemented subset and remaining limitation

Stripe exposes an optional `default_settings.default_payment_method` update. However, a phase's own payment method overrides that default. Changing explicit phase settings requires supplying every current/future phase and every setting to retain; omitted phase settings can be cleared. Updating an active phase also updates the underlying subscription. See [schedule inheritance and update semantics](https://docs.stripe.com/billing/subscriptions/subscription-schedules) and the [schedule update endpoint](https://docs.stripe.com/api/subscription_schedules/update).

A subscription-only method update cannot guarantee the chosen card remains effective after a scheduled transition. Updating only the schedule default also cannot cover explicit phase overrides. The inherited path accepts null current/future defaults. Migration187 separately handles recognized explicit phases with a retained matching commercial snapshot and original discount intent, preserving past phases and inherited nulls while updating the schedule default and all applicable explicit methods.

`subscriptionPaymentSchedule.ts`, `subscriptionPaymentMethodServer.ts` and migration178 implement the default-only schedule update with an immutable target/baseline, canonical schedule and subscription fingerprints, separate stage idempotency keys and first-write clocks, read-first recovery and authoritative unchanged-commercial-field checks. Both schedule and current subscription must resolve to the chosen method before success. Each uncertain stage fails closed after its own 23-hour retry window unless reads already establish the intended result. Shared plan/lifecycle guards preserve an uncertain-write hold across lease expiry. No provider snapshot is automatically restored. These controls are locally tested; they are not provider-tested in the actual sandbox.

The documented explicit-phase API requires a complete phase update. The bounded187 path supplies the reviewed pinned mapping, shared app guard, immutable stages, fresh preflight and full commercial readback. It cannot guarantee serialization with an uncoordinated external Stripe operator; this is an operational boundary, not an invented blanket prerequisite preventing implementation. Arbitrary unknown or ambiguous schedules are not admitted, and no schedule is released/recreated to bypass a refusal.

The corrected build passed after removing only a malformed generated `.next/dev` validator left by overlapping dev/build checks; no source assertion or TypeScript gate was bypassed.
