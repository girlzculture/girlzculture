# Selected-client email updates — local acceptance

COMMS-04 has a bounded owner workflow at Messages → Client updates. It uses the existing marketing content, communication preferences, canonical notification log, email transport and unsubscribe capability. This is implemented code with local automated evidence; no real email, production migration or hosted acceptance has occurred.

## Implemented boundaries

- The current owner chooses a current published marketing revision and up to20 individual eligible clients. The only offered channel is email. Published content is not permission to send; saving and separately approving a campaign send nothing.
- Each client must be registered, active, have a completed service at this business, a verified email, and current business-level marketing/email opt-in. Guest booking-only consent is excluded. Selection lists are scoped before projection, searchable and bounded to200 with an explicit cap notice. The interface shows masked email hints; provider addresses stay server-side.
- Saved campaigns freeze exact reviewed copies, canonical booking destination, recipients, consent revision, destination and language. Owners review every recipient language before approval. Each subsequent explicit send click handles one approved pending recipient. This keeps requests bounded and makes a partial campaign visible. The recent campaign list is bounded to50.
- Approval rechecks current content and all selected consents. Dispatch repeats owner, public-source, channel, registered-customer and consent checks. Changed copy/price, expired publication, opt-out, changed locale/revision/address or unavailable channel cannot silently use old approval.
- A database transaction reserves the existing notification log and a permanent recipient attempt before any provider call. The campaign/customer key prevents duplicate delivery across that customer's bookings. Concurrent requests serialize through the business/campaign locks. Processing attempts are never reclaimed, even after provider idempotency retention expires.
- Provider acceptance is labelled **Accepted by email provider**, never delivered/read. Timeout, abort, missing receipt or provider error becomes **Uncertain — support review needed**, with a sanitized incident reference. No automatic or user-triggered retry of that recipient exists. If final database write/readback fails, the processing latch still prevents a second provider call.
- Cancellation skips only unstarted recipients and labels them **Cancelled before sending**, separately from a fresh eligibility failure. It cannot recall an already attempted email. Each successful API response rereads the scoped workspace and verifies the affected saved record; failures retain entered selection and exact support references. Campaign save UUIDs survive response loss.
- New tables are private with RLS and no anonymous/authenticated table privileges. All new functions use SECURITY INVOKER with service-role-only execution and fresh owner authorization. No second messaging or money ledger is introduced.
